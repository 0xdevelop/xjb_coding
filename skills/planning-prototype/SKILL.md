# 规划原型

产出自包含 HTML 原型，看完就能落码，不用再翻别的文档。同一份数据出三个粒度：综合、产品、技术。

## 用法

```
/planning-prototype <需求名>
/planning-prototype <需求名> --stages-only     # 先只列阶段划分与发起方，确认后再画界面
/planning-prototype <需求名> --out <文件路径>   # 指定输出路径
```

产出物命名：`<功能域>_规划原型_<日期>.html`，落在目标项目的文档目录。

## 开工前的交互问询

原型的价值全在字段准不准。缺料就动手，画出来的是想象，不是需求。

**顺序：先自己查，查不到才问，一次问齐。** 能从仓里、文档里、方法表里拿到的，不许拿去问人——问了就是把自己的活推给对方。

### 八项必备

| # | 必备项 | 先去哪查 | 查不到才问 |
| --- | --- | --- | --- |
| 1 | 功能域名称与一句话目标 | 用户这句话本身 | 「这轮原型覆盖到哪一步为止？」 |
| 2 | 涉及哪几端、各自角色 | 项目架构文档、已有原型 | 「除了需求方端和运营端，还有别的端参与吗？」 |
| 3 | 阶段划分与每段发起方 | 已拍板的方案文档 | 先提一版划分请对方确认，**不要让对方从零列** |
| 4 | 服务端方法表或其快照位置 | 仓内搜方法注册表 / 快照文件 | 「方法快照在哪个路径？」 |
| 5 | 工作流定义体位置与编号 | 仓内 `workstream_*.json` | 「这条链用到哪几个定义体？」 |
| 6 | 外部服务方对接文档 | 项目文档目录下的对接文档原件 | 「对接文档原件在哪？」 |
| 7 | **需求自带的界面截图 / 设计稿** | 需求目录下的图片附件目录 | 「这轮有没有画好的界面图？在哪？」 |
| 8 | 输出路径与文件名 | 项目惯例 | 默认 `<功能域>_规划原型_<日期>.html`，无异议就不问 |

### 问的方式

- **一次问齐**。把缺的几项合成一条消息问完，不要一项一答挤牙膏。
- **带默认值问**。每项给出你的推荐，对方回「按默认」就能过，而不是逼人从零写。
- **先提再确认**。阶段划分这类，先提一版自己的划分请对方改，比让对方列清单快得多。
- **问完即停**。拿到答复前不要先画——画错了返工比多问一句贵。

### 可以不问就开工的情况

八项都能从仓里查齐，且阶段划分有拍板记录可依。这时直接出原型，在原型顶部标明每项的出处，让对方核对出处而不是核对结论。

## 五条硬规矩

1. **只有一份数据源**。多份内容看着全面，实际是同一批界面在几处漂，改一处漏两处。允许输出多个文件，但**必须由同一个生成脚本、同一份数据出**，禁止手工维护第二份。
2. **这个阶段不落码**。只出原型；原型定稿前不碰业务代码。
3. **字段不许编**。每个字段名、必填性、接口路径都要有出处。写不出出处，就不要写进原型。
4. **类型声明是断言不是校验**。返回值形状不能只看 Go / TypeScript 的类型声明，要么打真接口看回包，要么读服务端真正拼返回值的那几行代码。
5. **判据唯一**。界面开不开闸只看服务端给的可执行动作列表与可选性字段，原型里不画「前端自己算」的分支。

## 两端职责的默认分界

沿用，不要每次重新定；要改先找拍板记录。

| 类别 | 归谁 | 依据 |
| --- | --- | --- |
| 专业判断（定规模、填技术规格、受理例外、放行方案） | 需求方端 | 代客不得代到专业判断上 |
| 与外部服务方交涉（录回执、录结果） | 运营端 | 恒由平台发起 |
| 执行段（提交作业一类，不含专业判断） | 需求方端；代客路径运营端可代起 | — |
| 外部方标识与原文（外部作业号、批次号、单号、错误码、原始回包） | **只在运营端** | 需求方端一处不出现 |

**边界要具体到字段。** 同一条指标偏差，需求方端写成人能判断的结论（「实测值 86，阈值 90 · 仍可用」），运营端才出原始字段名、外部错误码与来源方。只写「运营端能看到外部信息」等于没写。

## 动手前必答的七个问题

每一段都先答完再画，答不上就是还没摸清。

| 序号 | 问题 |
| --- | --- |
| 1 | 这一段由哪一端发起？发起动作的标识是什么？ |
| 2 | 具名确认点是哪个？确认人姓名之类的字段是不是外部合同要求的？ |
| 3 | 落到哪个工作流定义体的哪几个任务？ |
| 4 | 打外部服务方哪个接口？必填哪几个参数？ |
| 5 | 返回值里哪些要回报给业务事实源？回报方法与必填是什么？ |
| 6 | 失败怎么走——重试、退回、还是正常终结？**分清「终局但不是失败」**：可选集合被逐轮消耗到不足以继续时，该给「终结 / 重来一轮」，不是报错重试。 |
| 7 | 哪些字段属于外部服务方事实，必须挡在需求方端之外？ |

## 一份原型的形状

单个 HTML，自带样式与脚本，无外部依赖，不引 CDN。

### 导航：两级 + 编号 + 颜色分组

照搬目标产品自己的导航层级，不要自创一套。产品是「一级阶段 → 二级子视图」步进式的，原型就画两级。

- **一级阶段**一排彩色按钮，每个阶段一种颜色，点它跳到该阶段第一个子视图。
- **二级子视图**按归属<b>框进一个同色边框的盒子里</b>，盒子左上角浮一个标签写「<编号> <阶段名> · N 个二级」。颜色 + 框体让人一眼看出归属，不用逐个读字。
- **每个子视图一个稳定编号 `<一级序号>.<二级序号>`**（`1.1` `3.4`）。编号是这份原型的通用地址：沟通、提交信息、check 项、验收全带编号不带描述。**编号一旦发出去就不再变**，插入新子视图宁可排到末位。
- 每个子视图节点带 `data-no` / `data-lv1` / `data-view` 三个属性，让 agent 不靠视觉就能解析出归属与路由。
- **产品侧没有对应处理面的子视图，显式写「无 X 参与」**，不要让它从导航里消失——消失了读者会以为是漏画的。

一级阶段被需求合并时（两个阶段并成一个），在原型顶部写清合并前是哪两个、原来各带哪些子视图，否则读者对不上现网。

### 「第 N 次」不是导航维度

轮次、批次、版本、重试次——凡是**同一形态跑第二遍**的东西，都是**页面内的一个维度**，不是二级导航项。先去产品里核一遍：那个次数在现有实现里是挂在哪儿的（一个 `xxx_round_id` 入参？右栏一张卡？一个筛选器？），照着它画。

- **同一份 DOM 换那个 id**，页面内给一条切换条（`第 1 轮 / 第 2 轮 / 两轮对照`），不要为第二次另开一个子视图。
- **随次数变化的可选性（额度缩量、档位锁定、按钮解禁）不需要独立界面**——它们是「当前次 + 剩余额度」两个值算出来的，给第二次另画一版等于把同一条规则维护两处。
- **例外只有一种**：第二次出现了第一次根本不存在的**新动作**（比如「下一轮怎么做」的模式选择 + 具名确认），没有可复用的上一次形态，这才配一个独立子视图。

自检：如果两个子视图的界面元素几乎一样、只差一个次数值，那就是拆错了，合回去。check 项里写着「与上一次复用同一组件」却又画了两个子视图，是自相矛盾——以 check 项为准。

### 界面要画实，靠缩放不靠省略

每一屏按固定设计宽度写足细节——真实字段名、真实数值、真实状态、真实校验结果。对照区用 `transform: scale(列宽 / 设计宽度)` 等比缩小。

**「放大」是放大到看得清局部，不是回到设计尺寸。** 设计宽度在大屏上往往比对照区还小，`scale(1)` 等于没放大。按视口宽算倍率并设上限免糊：

```js
const k = Math.min(2.2, Math.max(1.15, window.innerWidth * 0.94 / 设计宽度));
```

**两处必须是同一份 DOM**：写一个 `frame(端, 子视图)` 函数产出界面，对照区与放大层都调它。绝不为缩略图另写一版简化的——那是两套内容，改一处漏一处。

判断标准：把缩略图放大后，能不能直接照着填代码？带真实数值与单位的（「已锁定 40 条」）是实；「显示数量」这种描述句是虚，重写。

### 读者分层：综合 / 产品 / 技术

同一份原型有两类读者，需要的粒度差一个量级：

- **提需求的人和会议**：要知道每一屏谁在用、他在这屏干什么、这次改什么、有什么要他拍板。字段名、接口名、代码行号对他们是噪音——**噪音多了，该他拍板的那几条反而没人看见**。
- **落码的人**：要接口、要传参、要判据、要出处行号，产品讲法对他们是废话。

所以顶部给一排**视角开关**，切的是「露出哪些页签 + 细节密度」，**不是三份内容**：

| 视角 | 露出什么 | 什么时候用 |
| --- | --- | --- |
| 综合 | 全部 | 自己看、两边一起过 |
| 产品 | 产品讲法、界面、要拍板的问题；出处行、隔离线、等宽字体的技术标注全收起来 | 开会、给提需求的人看 |
| 技术 | 界面、接口传参、check 项、路径分支；产品讲法收起来 | 落码 |

实现要点：

- 视角是 `body` 上的一个属性，靠 CSS 收放，**同一份 DOM**。给技术专属块一个类、产品专属块一个类，各自在对方视角下 `display:none`。
- **导航项的副标题也要分版**：技术视角显示真实路由，产品视角显示一句中文（「选这轮做多少条」），不要让提需求的人对着路由名猜。
- 初次进来按视角落到各自最该先看的那一页；手动切视角时，当前页在新视角里还有就别把人弹走。
- **再出几份单视角文件**（产品版 / 技术版），把视角钉死、切换器收起来，方便直接发出去。**必须同一脚本同一份数据生成**，并在页眉互相留链接，写明「内容同源」。

### 产品视角怎么写

每一屏四段，**一句技术黑话都不许有**：

| 段 | 写什么 |
| --- | --- |
| 谁在用这屏 | 哪个角色。多方参与时写清谁主动、谁只能看 |
| 他在这屏做什么 | 一两句话说清这屏的事，用他熟悉的业务词 |
| 这次要改什么 | 逐条列，每条都能对上需求里的某一项 |
| 要请产品定的 | 只列**他答得上来的**：要不要这个功能、用户该不该能点、某块撤不撤。答不上来说明分错类了 |

再给一页**「要产品定的事」汇总**：编号 / 在哪一屏 / 要定什么。只收产品能答的那类，接口能力问外部方、技术形态自己定，两类都不许混进来。定完让对方在编号上回一句，落码按编号走。

自检：把产品视角念给一个不写代码的人听，他能不能复述出这一步在干什么、要他定什么。念不出来就是还没写成人话。

### 视角切换：四个页签

| 页签 | 内容 | 定位 |
| --- | --- | --- |
| 两端界面 | 左右两屏并排对照。页面路径、真实控件（可选 / 置灰 / 必填标记）、等待态、边界提示。**置灰控件必须写明原因**，不是让它消失。 | **画的是必要承载元素（交互动作 + 数据字段），不是最终 UI 稿。** 字段名、必填性、置灰原因、失败去向是契约不能改；配色、排布、控件形态会变，以设计稿为准。**这句话要写在页签里**，否则读者把它当视觉稿评审。 |
| 调用链与传参 | 步骤 / 发起方 / 调用 / 入参 / 说明与返回值 / **力度** / **关联 check 项**。一行一跳，从界面动作到服务端方法、到工作流任务、到外部接口、到回报方法，一条不省。下面跟一张关键字段表：字段 / 来源 / 必填 / 去向与约束。 | 定接口。 |
| 各端 check 项 | 见下节。 | 定工作量与进度。 |
| 路径差异 | 同一功能有两条以上发起路径时（谁付费、谁审批、内部 / 外部、试用 / 正式之类），**逐子视图**列：维度 / 路径 A / 路径 B / 处理方案。 | 定分支。只有一条路径时这个页签不要。 |

### 「各端 check 项」是进度事实源

这一页不是罗列愿望，是开发和产品经理**后续更新进度的主要落点**，必须能当 check 板用。

**每项六列**：编号 / 端 / check 项 / 力度 / 链步 / 前置依赖 / 状态。

- **编号** `<子视图编号>-<端首字母><序号>`，如 `1.2-P3`、`3.4-A1`。**跨版本不变。**
- **端**：写具体仓名或角色，不写「前端」这种泛称。
- **check 项**：写具体动作与可观察结果，不写「要健壮」。
- **力度**：`已有` / `改` / `新增` / `弃用` 四值，**与调用链那一列同一套值域**。`弃用` 是真实力度——需求要求撤掉某块展示时，它不是「改」。
- **链步**：钉到「调用链与传参」的哪一步（`①` `②`）。纯界面项写 `—`。**同一个圈号下有并列两条腿时（同一步的两种发起方式），token 要写成 `①路径A` / `①路径B` 这样可区分的前缀**，否则两条腿的 check 项会互相串。
- **前置依赖**：卡在谁身上。没有就写「无」。
- **状态**：`待办` → `已提交(提交号)` → `已部署`；**`待定` 表示还卡在外部依赖上，不进排期**。

**双向联动**：调用链表反查「这一步牵出哪些 check 项」，check 表正查「这一项落在哪一步」。两张表对不上就是有一边漏了。

除了当前子视图那张表，再给一张**全量 check 板**（所有子视图汇总，当前子视图的行高亮）。产品经理看总账、开发看自己那几行，一个页面够。

## 怎么取到真字段

| 来源 | 取法 |
| --- | --- |
| 服务端方法的入参与必填 | 从方法注册表或其落盘快照取；快照过期先重新生成再取，不要凭印象补。 |
| 工作流定义体的任务与外部接口 | 解析定义体 JSON。**任务通常不在顶层**，先打印一层结构看清嵌套路径再取，别按印象写路径。 |
| 外部服务方的必填与返回值 | 只认对接文档原件，不认转述，不认二手摘要。 |

```bash
# 工作流定义体：任务标识 / 别名 / 请求方法 / 请求地址
python3 -c "
import json
d=json.load(open('<定义体 JSON 路径>'))
for st in d['steps'].values():
    for stage in st.get('stages', []):
        for t in stage['tasks']:
            print(t['task_id'], t.get('alias'), t.get('request_method',''), t.get('request_url',''))
"

# 方法快照：某个方法的必填与全部可选键
python3 -c "
import json
m=json.load(open('<方法快照路径>'))['methods']
print(json.dumps(m['<方法名>'], ensure_ascii=False, indent=2))
"
```

### 三种事实源，优先级与提问分工

一个需求通常同时有三种材料，**职责不同，不能混用**：

| 材料 | 它定什么 | 不定什么 |
| --- | --- | --- |
| 需求正文 | **方向**：要改成什么样、为什么改、哪些撤哪些留 | 不定界面长相，用词也不是字段名 |
| 需求自带的界面截图 / 设计稿 | **形态**：屏怎么分、控件怎么摆、文案逐字、表有哪几列 | 不定接口与判据，画稿可能漏画或用旧名 |
| 代码现状 | **现状**：眼下实际是什么样、哪些已有 | **不定应该是什么样**（可能只是迁移到一半） |

**有截图就必须先逐张看完再动手。** 拿口头约束加代码现状去脑补界面，是这类任务里最贵的错误——画完十几屏才发现整段结构错，返工成本远高于先花时间把图看完。看图时逐张记：屏标题、卡头、每个控件的文案逐字、表的列名逐字、按钮文字、状态角标、分页信息。

**三者打错架时**：方向听正文，形态看截图，现状只当参照。冲突处**并列写进原型**，标明「待确认」，并写清**该问谁**：

| 拿不准的事 | 问谁 | 怎么问 |
| --- | --- | --- |
| 要不要这个功能、用户该不该能点、某块撤不撤 | 产品经理 | **用大白话**。产品经理常常不是工程背景，问题里不要出现字段名、状态机、接口名 |
| 外部方能不能给这个数、按什么口径给 | 外部服务方 | 带接口名与字段名，要口径不要承诺 |
| 放哪个页面、组件怎么拆、参数怎么传、某个态要不要禁用 | **我们自己定** | 不要推给产品经理——把技术形态当问题抛过去，既问不出答案又拖进度 |

自检：一条「待确认」如果产品经理答不上来，说明分错类了，重新归。

**架构与职责归属类问题不许从代码推断。** 谁拥有这个能力、这一段该归哪一端，去找拍板记录的原话；找不到就问人。现状可能只是迁移到一半的形状。

## 常见跑偏

| 跑偏 | 为什么是坑 |
| --- | --- |
| 把跨接口的组合逻辑放进网关层 | 网关长出业务逻辑，就成了第二个定义能力的地方。同一条规则两处维护，迟早对不上。方法表是唯一定义能力的地方，各对外面只是薄承载。 |
| 代客代到专业判断上 | 发起动作与具名确认必须同归一方。分开之后确认只剩追认，签的名对不上做的事。 |
| 拿「代码现状」当「应该如此」 | 尤其注释里写着「本轮不改」的地方，那是债不是规范；照抄等于把债浇成水泥。 |
| 只画顺利路径 | 落码时每人各编一套走法，上线才发现同一个失败有三种结局。 |
| 两端各算各的判据 | 同一件事算出不同结果，用户看到能点、运营看到不能点，谁都说不清哪个对。 |
| 把「终局」画成「失败」 | 该正常终结的路径给了「重试」，用户反复点一个必然失败的按钮。 |
| 有界面截图却不看，拿口头约束和代码现状脑补 | 画完十几屏才发现整段结构错。截图里那些逐字文案、表列名、按钮文字，是脑补不出来的。 |
| 把需求正文的用词当字段名 | 提需求的人常常不是工程背景，「取消某个数量选择」可能是指「把这个选择器从这一页挪走」，不是「这个参数不要了」。按意图翻译，别按字面落码。 |
| 把技术形态当问题抛给产品经理 | 既问不出答案又拖进度。该自己定的自己定。 |
| 把「第 N 次」拆成新的二级导航项 | 两个子视图界面几乎一样、只差一个次数值，改一处漏一处。次数是页面内维度。 |
| 同一个动作放两个入口 | 两处各自演化判据，迟早一处能点一处不能点。发现重复要当场撤掉一处，并在保留那处写明「入口只在这里」。 |
| 把两条发起路径画成一个页面两套按钮 | 读者分不清哪套属于自己，落码时也会写成运行时 if。按路径二选一渲染，不属于本路径的入口**不渲染**，不是置灰。 |
| 拿其中一条路径的状态枚举去渲染另一条 | 同一列双值域、按路径字段分属两组枚举是常见设计；取值前先看那个决定路径的字段，否则整列渲染全落空。 |
| 给不同读者各写一份内容 | 三份文件三套说法，改一处漏两处。**一份数据，多个粒度**，文件可以多，内容源只能一个。 |
| 产品视角里留着字段名和接口名 | 该他拍板的几条被噪音淹了，会开完什么也没定。 |
| 把「两端界面」当 UI 稿评审 | 它承载的是元素与字段，视觉会变。不写明这句，评审会耗在配色上，契约反而没人看。 |

## 交付前自查清单

- [ ] 所有输出文件由**同一脚本同一份数据**生成，没有手工维护的第二份；无外部依赖
- [ ] 顶部有综合 / 产品 / 技术视角开关；产品视角下出处行、隔离线、技术标注、路由名都收起来了
- [ ] 产品视角每屏四段齐全，通篇没有字段名、接口名、代码行号
- [ ] 「要产品定的事」只收产品答得上来的，接口能力与技术形态没混进来
- [ ] 「第 N 次」（轮次 / 批次 / 版本）做成页面内切换，**没有为第二次另开子视图**；确实是新动作的那个除外，且写明了它为什么独立
- [ ] 导航照搬产品自己的两级层级；一级按阶段上色并框住所属二级；每个子视图有稳定编号 `x.y` 与 `data-no` / `data-lv1` / `data-view`
- [ ] 界面按固定设计宽度画实，对照区等比缩放；**「放大」放大到看得清（倍率按视口算，不是 `scale(1)`）**；缩略图与放大层是同一份 DOM
- [ ] 「两端界面」页签里写明了「画的是必要承载元素，不是 UI 稿」
- [ ] 每屏的数值、状态、校验结果都是具体值，没有「显示 XX」这类占位描述
- [ ] 每一段的七个问题都答全，答案落在原型里，不是留在聊天记录里
- [ ] 每个字段都有出处（方法快照 / 定义体 / 对接文档），无一处凭印象
- [ ] 每一段至少写清一条失败去向，且分清重试 / 退回 / 正常终结
- [ ] 每个置灰控件都写了置灰原因
- [ ] 边界提示具体到字段名，不是「注意权限」这类空话
- [ ] check 项六列齐全，编号 `x.y-P/A n` 稳定，力度用 `已有 / 改 / 新增 / 弃用`，`待定` 项写明卡在谁身上
- [ ] check 项与调用链**双向对得上**：每一步牵出的 check 项、每一项钉的链步，两边都查得到
- [ ] 有两条以上发起路径时，出了「路径差异」页签，且**逐子视图**给了处理方案，不是只写一段总述
- [ ] 取字段用的命令**真跑过一次**，不是照抄模板
- [ ] 八项必备在开工前已补齐，靠查得到的没去问人
- [ ] **需求自带的界面截图逐张看完了**，不是挑几张看
- [ ] 每处「正文 / 截图 / 现状」打架的地方都并列标了出来，并写明该问谁（产品意图 / 外部接口 / 我方自定）
- [ ] 没有落任何业务代码

# 产品验收闭环（项目约束）

本文件是 xjb_coding 的**项目约束**，不是可选建议、过程备忘或一次性说明。由 `start_coding.md` 的四层门禁 L4、§9 项目特定约定区，以及完工验收引用。模板仓 `project_template_go` 的项目内正文是根目录 `docs/product_acceptance.md`，实例应同步遵循同一套闭环，而不是另写一套。

## 1. 适用范围

在下列任一条件下，本规范对目标项目强制生效：

- 项目由 `project_template_go` 实例化，或保留该模板的 `git_tag.sh` / `build.sh` / GitHub Actions 发版链路与官方安装脚本；
- 项目以 GitHub Release 资产交付，并提供官方安装脚本和 systemd 服务。

不适用的项目（库、Skill、插件、无安装交付物的工具仓等）不因本文件扩大验收范围。本 Skill 仓库自身也不按本闭环做 systemd 安装验收。

适用时，过程增强（联动补强、隔离回退、复用已有环境的推理、本地打包试跑等）只是过程证据，**不是最终预期**。最终预期是下面的闭环全部实际走通。

## 2. 验收闭环（必须全部实际发生）

产品验收通过，当且仅当下列步骤都已在目标环境**实际发生**，并且根目录 `docs/` 留下对应实测文档：

1. **从 GitHub Release assets 下载**对应架构（及项目规定的产品包）。必须使用该 Release 的资产 URL。禁止用本地 `build/`、打包目录、手工拼装的半套包或其他非 Release 产物冒充 GitHub assets 验收。
2. **用项目自带安装脚本**部署到**脚本写明的根目录**。模板默认是 `/${APP_NAME}`（例如模板本身为 `/project_template_go`）。禁止自行改安装前缀，禁止改装到 `~/.local/share` 或其他未由官方脚本指定的路径。
3. **systemd 服务启动**成功，单元与脚本声明一致。
4. **跑完全程并得到预期业务结果**。所宣称的任务、步骤、产物必须真实发生并可核对（路径、哈希、日志、查询结果等）。
5. **按官方脚本卸载**（模板安装脚本中的 uninstall 选项），并核对服务已停止、单元已移除、脚本声明的安装根目录已清理。
6. **在项目根 `docs/` 留下详细测试过程文档**；根 `README` 只保留短说明并使用相对链接，不把全过程写进 README。

缺任一步，或某步只是计划、演练稿、局部测试、复用旧环境的结果，都不能把产品验收标为通过，也不能把实现进度写成 `ACCEPTED`。

## 3. 发版底稿（模板契约，禁止擅自重设计）

发版链路必须以 `project_template_go` 的下列底稿**复制后做必要的小幅增量适配**，禁止重新设计入口、默认语义或生命周期：

- 无参 `./git_tag.sh` 就是模板既有发版入口（脚本亦接受 `auto`，与无参走同一路径）。它会递增版本、生成文档、提交并推送**轻量 tag**。禁止把无参改成默认只读、另加 `--publish` 才发布、把默认轻量 tag 改成附注 tag，或把交互式 `custom` 变成默认入口。
- `build.sh` 由 GitHub Actions 的 Build 作业调用，负责构建与打包。
- GitHub Actions 保持三段顺序：`release` → `Build` → `RemoveOldRelease`。禁止重排、拆掉或改掉原有清理行为来迁就实例。模板里移动 `latest`、清理旧 Release/tag 的行为按原样保留；需要实际执行这些清理时单独按脚本与工作流进行，不在工作流外擅自补做或取消。

允许的增量适配仅限有依据的项目差异，例如额外产物、原生多架构 runner、CGo / 实际 Go 版本、全部包校验通过后再上传。这些适配不能成为改掉上述契约的理由。不要改模板仓的 `git_tag.sh` 契约来迁就某个实例。

发版本身不等于产品验收通过。无参 `git_tag.sh` 会推 tag 并触发上述三段；未获授权不要执行发版。产品验收必须等到 Release 资产可下载之后，再按第 2 节走安装与业务闭环。

## 4. 测试过程文档（只记录已发生的事实）

实测文档放在项目根 `docs/`（例如 `docs/acceptance_<date>.md` 或项目既定文件名），并在根 README 用相对路径做短链。文档必须记录实际发生的内容，至少包括：

- 实际执行的步骤与命令；
- 实际发生的时间，并标明时区（禁止把计划时间写成发生时间）；
- Release 页面与 asset 的 URL、资产名称、校验和（若有）；
- 官方安装脚本路径、脚本写明的安装根目录、实际安装路径、systemd 单元名与启动结果；
- 任务、步进、产物等业务事实（路径、哈希、查询或日志摘录）；
- 官方卸载的命令或选项、卸载后的核对结果；
- 未覆盖项与限制（例如未做的架构、未授权的外部依赖、科学质量未验证等）。

禁止把计划写成已发生。禁止伪造业务结果。禁止在未做相应验证时，把预测或实验结果的科学质量写成已获验证。

L1 编译测试全绿、本地构建包、隔离夹具、复用已有环境与权重的推理，都可以作为过程证据写入文档，但必须标明范围，不能替代本闭环，也不能写成「已从 GitHub assets 完成正式安装验收」。

## 5. 提交与文档入口

- 提交作者只记录人类用户本人；禁止任何协作者信息，包括 AI / Cursor / `Co-authored-by` 及其他 agent 标识。提交后核对完整 message。禁止 force-push（含 `--force` 与 `--force-with-lease`）。已推送历史不擅自改写。
- 操作说明与实测过程写在根 `docs/`；README 只做短说明和相对链接。
- 只精确添加本任务文件；不把目标项目的 `.auto_coding/` 工作区提交进 git。
- 不打印、不改写受保护配置与秘密。

## 6. 执行纪律

执行者按已明确标准自行核对每一步证据，不把用户当验证者，不靠反复确认推进已明确的工作。仅在缺少用户才能提供的硬授权或凭据（例如尚未授予的发版、正式安装、部署凭据）时停止，并说明缺的是哪一项。

本约束由 `start_coding.md` §1.1 项目自检发现适用对象后生效；§1.5 完工验收必须引用根 `docs/` 实测文档；适用时 L4 不得视为空集。§9 用于填写本项目的安装根目录、官方脚本路径和预期业务结果，不填写也不能使本约束失效。
